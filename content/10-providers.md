# 10 · provider마다 다르다 — 누가 컨텍스트를 소유하는가

> **한 줄 요약:** 앞 장들의 정책은 모든 모델 호출에 똑같이 적용되지 않으며, "누가 컨텍스트를 소유하는가"가 자동 압축의 주체와 생략되는 단계를 정합니다.

## 이 장에서 배우는 것

- 컨텍스트 "소유권"이 무엇이고, 왜 정책을 갈라놓는지
- 세 가지 주요 경로(이 하네스 일반 관리, OpenAI remote 대상, resident Claude SDK)의 차이
- 원문이 특히 경고하는 두 가지 오해와, 정책이 모델 이름으로 정해지지 않는 이유

## 왜 이 이야기를 하는가

앞 장들에서 토큰을 줄이는 장치를 여럿 살펴봤습니다. 규칙으로 줄이는 축소가 있었고, 오래된 대화를 바꾸는 요약도 있었습니다. 이것들을 읽고 나면 "모든 모델 호출이 이 순서를 거치는구나" 하고 생각하기 쉽습니다.

그런데 그렇지 않습니다. 이 장치들은 모든 호출에 공통으로 붙는 절차가 아닙니다. 어떤 경로에서는 일부가 빠지고, 어떤 경로에서는 거의 다 물러납니다.

이유는 하나입니다. **대화 기록을 누가 들고 있느냐**가 경로마다 다르기 때문입니다.

## 컨텍스트 소유권이란

::: term 용어 · 컨텍스트 소유권
이번 요청에 어떤 대화 내용을 보낼지, 그리고 그것을 언제 요약할지를 결정하는 주체가 누구인지를 뜻합니다.
:::

크게 두 가지 상황이 있습니다.

1. **이 하네스가 요청 메시지를 직접 만드는 경로.** 하네스가 저장된 기록에서 보낼 내용을 고릅니다. 이것이 앞에서 배운 요청 투영(request projection)입니다. 이때는 하네스가 컨텍스트의 주인입니다.
2. **SDK가 자기 세션을 직접 유지하는 경로.** SDK는 provider 쪽 소프트웨어 묶음입니다. 이 경우 대화 기록은 SDK가 들고 있습니다. 하네스는 그 위에서 일을 시키기만 합니다.

::: analogy 비유 · 누구의 책상인가
내 책상이라면 내가 언제 치울지 정합니다. 남의 책상을 빌려 쓰고 있다면, 치우는 일은 책상 주인이 합니다. 내가 멋대로 서류를 버리면 주인의 정리 방식과 충돌합니다.
:::

코드는 이 소유권을 먼저 판정합니다. 그 판정 결과로 두 가지가 정해집니다.

- 자동 압축(컴팩션)을 누가 맡는가
- 요청을 보내기 전 축소 단계 중 어떤 것을 건너뛰는가

## 세 가지 주요 경로 한눈에 보기

아래 표는 원문이 정리한 주요 기본 경로를, 토큰을 줄이는 관점에서만 다시 묶은 것입니다. 칸 이름부터 풀어 두겠습니다.

- **요청 축소:** 보내기 전에 규칙으로 내용을 줄이는 단계입니다. LLM을 부르지 않습니다.
- **요약 방식:** 그래도 부족할 때 누가, 어떻게 요약하는지입니다.
- **주의할 경계:** 그 경로에서 헷갈리기 쉬운 조건입니다.

| 경로 | 요청 축소 (규칙으로 줄이기) | 요약 방식 | 주의할 경계 |
|---|---|---|---|
| 이 하네스 일반 관리 | 기본 순서는 admission → reduction → emergency | 하네스가 자동 압축을 맡음 | 각 단계는 설정, 사용량, breaker 조건을 따름 |
| OpenAI remote 대상 | 일반 reduction은 기본 제외. admission과 emergency는 유지 | blocking/core 경로는 remote compaction을 먼저 시도 | 대상 판정에 맞는 모델만 해당. 모든 OpenAI 모델이 아님 |
| resident Claude SDK | SDK가 컨텍스트를 소유하면 하네스 축소 파이프라인이 물러남 | SDK가 맡음. 하네스의 자동 압축과 degradation 감시도 물러남 | `resumeMode: off` 또는 compaction 모델 override가 소유권을 바꿀 수 있음. 수동 압축은 별도 경로 |

::: warn 주의
이 표는 모든 갈림길을 다 적은 상태 전이표가 아닙니다. 주요 경로의 기본 구분일 뿐입니다. 예를 들어 breaker fallback 같은 조건은 일반 reduction의 관문을 따로 우회할 수 있습니다.
:::

## 경로 1 · 이 하네스 일반 관리

가장 기본이 되는 경로입니다. 하네스가 컨텍스트의 주인이므로 앞 장들의 장치가 대부분 살아 있습니다.

요청은 세 단계를 차례로 거칩니다.

1. **admission:** 큰 도구 출력이 기록에 들어오기 전에 크기를 제한하는 단계입니다.
2. **reduction:** 규칙에 따라 보낼 내용을 줄입니다. LLM을 부르지 않습니다.
3. **emergency:** 그래도 넘칠 때 쓰는 비상 단계입니다.

이 세 단계로도 모자라면 하네스가 직접 요약을 만듭니다. 1층(규칙으로 자르기)과 2층(요약으로 바꾸기)이 모두 하네스 손에 있는 경로입니다.

다만 각 단계가 항상 도는 것은 아닙니다. 설정, 사용량, breaker 조건을 통과해야 실제로 실행됩니다.

## 경로 2 · OpenAI remote 대상

이 경로에서는 요약을 provider 서버 쪽에 맡길 수 있습니다. 그래서 하네스가 직접 하던 일 일부가 빠집니다.

**빠지는 것**

- 일반 reduction은 기본적으로 제외됩니다.

**남는 것**

- 하네스 관리 경로의 admission과 emergency는 유지됩니다.

그리고 blocking/core 경로, 즉 요약이 꼭 필요해 기다려야 하는 경로에서는 remote compaction을 먼저 시도합니다. 서버에 요약을 부탁하는 방식입니다.

왜 이렇게 나눌까요? 서버가 컨텍스트 정리를 맡을 수 있는데 하네스가 같은 일을 하면 일이 겹칩니다. 그래서 겹치는 부분만 덜어 내고, 넘침을 막는 안전장치(admission, emergency)는 남겨 둔 구조로 읽을 수 있습니다.

::: warn 주의 · "OpenAI remote 대상" ≠ 모든 OpenAI 모델
이 경로는 **대상 판정에 해당하는 모델에만** 적용됩니다. 이름이 OpenAI라는 이유로 모든 OpenAI 모델이 여기에 속한다고 생각하면 적용 범위를 잘못 판단하게 됩니다.
:::

## 경로 3 · resident Claude SDK

여기서는 SDK가 세션을 직접 유지합니다. SDK가 컨텍스트를 소유하면 하네스는 크게 물러납니다.

- 하네스의 축소 파이프라인이 적용되지 않습니다.
- 하네스의 자동 압축이 물러납니다.
- degradation 감시도 물러납니다. 응답 품질이 떨어지는지 지켜보는 장치입니다.

남의 책상 비유 그대로입니다. 주인(SDK)이 정리하므로 하네스는 손대지 않습니다.

다만 이것은 **기본 동작**입니다. 소유권을 바꾸는 방법이 있습니다.

- `resumeMode: off` 설정
- compaction 모델 override(요약에 쓸 모델을 따로 지정하는 설정)

이 둘은 소유권을 하네스 쪽으로 바꿀 수 있습니다. 또 수동 압축은 자동 압축과 별개의 경로입니다.

::: warn 주의 · 기본값만 보고 단정하지 않기
resident Claude SDK의 기본 동작만 보고 "이 하네스는 이 provider에서 어떤 압축도 하지 않는다"고 결론 내릴 수는 없습니다. 소유권을 바꾸는 설정과 수동 실행 경로가 있기 때문입니다.
:::

## 정책은 모델 이름으로 정해지지 않는다

세 경로를 보면 공통점이 하나 있습니다. 어떤 축소 단계가 살아 있는지는 모델 이름표만 봐서는 알 수 없습니다.

::: note 핵심
실제 세션의 정책은 **모델 이름**으로 정해지지 않습니다. **연결 방식과 compaction 설정의 조합**으로 정해집니다.
:::

## 한 줄 정리

앞 장들의 축소와 요약 장치는 모든 호출에 똑같이 붙는 절차가 아닙니다. 컨텍스트를 하네스가 소유하는지, SDK가 소유하는지에 따라 축소 단계와 자동 압축의 주체가 달라집니다. "OpenAI remote 대상"은 모든 OpenAI 모델이 아니고, resident Claude SDK의 기본값이 "압축을 전혀 안 한다"는 뜻도 아닙니다. 결국 정책은 모델 이름이 아니라 연결 방식과 설정의 조합으로 결정됩니다.
