# 11 · 돈 이야기 — 왜 두 번째 호출부터 싸지는가

> **한 줄 요약:** 프롬프트 캐시 적중률이 몇 번의 호출 만에 100%에 가까워지는 것은 큰 고정 앞부분과 체크포인트 배치 덕분이며, 컨텍스트 정책은 그 앞부분을 괜히 바꾸지 않도록 돕는 역할입니다.

## 이 장에서 배우는 것

- 화면 하단의 `CH xx.x%`와 `/session`의 `Cached (xx%)`가 각각 무엇을 계산하는지
- 캐시 적중률이 왜 그렇게 빨리 높아지는지, 4번의 호출 예시로 확인하기
- Anthropic과 다른 provider가 캐시를 다루는 방식, 그리고 하네스가 캐시를 지키려고 둔 장치들
- 캐시가 깨지는 지점과, 정책과 적중률 사이의 올바른 인과

## 왜 이 이야기를 하는가

앞 장까지는 모델에 보내는 토큰의 '양'을 다뤘습니다.
토큰은 모델이 글을 세는 단위입니다.
대략 단어보다 잘게 쪼갠 조각이라고 보면 됩니다.

효율에는 두 번째 축이 있습니다.
보낸 토큰 가운데 얼마가 싼 값으로 계산되느냐입니다.
같은 양을 보내도 값이 크게 달라질 수 있습니다.
그 열쇠가 프롬프트 캐시입니다.

::: term 용어 - 프롬프트 캐시 (prompt cache)
직전 요청과 앞부분이 같으면 그 부분을 낮은 단가로 재사용하는 기능입니다.
provider, 즉 모델 호출을 처리하는 제공자가 이 기능을 제공합니다.
재사용된 토큰에는 일반 입력보다 낮은 단가가 붙습니다.
:::

::: analogy 비유 - 어제 이야기를 이어 가기
어제 한 이야기를 그대로 이어 가면 처음부터 다시 설명할 필요가 없습니다.
"어제 거기까지 했지?" 한마디면 됩니다.
하지만 이야기 앞부분을 조금이라도 바꾸면 처음부터 다시 설명해야 합니다.
프롬프트 캐시도 앞부분이 똑같을 때만 재사용됩니다.
:::

하네스가 손댈 수 있는 곳은 세 군데입니다.

1. 요청에 "여기까지 캐시해도 된다"는 표시를 붙이는 일
2. 요청과 요청 사이에 앞부분을 그대로 유지하는 일
3. 캐시가 만료되기 전에 다음 요청을 보내도록 시간을 관리하는 일

먼저 화면에 보이는 숫자가 무엇인지부터 정확히 보겠습니다.

## footer의 CH 숫자는 무엇인가

화면 하단 표시줄을 footer라고 합니다.
여기에 `CH xx.x%`가 뜹니다.
계산식은 이렇습니다.

```text
latestCacheHitRate =
cacheRead / (input + cacheRead + cacheWrite)
```

각 이름의 뜻은 다음과 같습니다.

- `cacheRead`: 캐시에서 읽어 재사용한 토큰
- `cacheWrite`: 이번에 새로 캐시에 써 넣은 토큰
- `input`: 캐시와 상관없이 일반 입력으로 계산된 토큰

분모는 이번 호출에 보낸 전체 토큰입니다.
분자는 그중 재사용된 토큰입니다.
그래서 이 값이 캐시 적중률, 즉 보낸 토큰 중 캐시에서 재사용된 비율이 됩니다.

### 세션 전체가 아니라 '가장 최근 한 번'입니다

이 숫자는 세션 누적값이 아닙니다.
가장 최근 assistant 메시지 하나의 비율입니다.
세션 관리자는 assistant 메시지가 기록될 때마다 이 값을 다시 계산해 덮어씁니다.
비율이 10% 미만이면 footer에 아예 표시하지 않습니다.

### assistant 메시지는 요청 단위가 아닙니다

여기서 헷갈리기 쉽습니다.
요청(request)은 사용자가 한 번 시킨 일입니다.
assistant 메시지는 모델 호출 한 번의 결과입니다.
모델 호출은 프롬프트 한 번을 보내고 응답을 받는 일입니다.

한 요청 안에서 도구를 다섯 번 쓰면 assistant 메시지가 다섯 개 생깁니다.
그리고 각각이 footer 값을 새로 씁니다.
그래서 사용자 요청 세 번이 호출 열 번 이상이 될 수 있습니다.
footer 숫자는 그 가운데 마지막 호출 하나만 보여 줍니다.

## /session의 누적 수치는 왜 더 낮은가

`/session` 정보 화면에는 `Cached (xx%)`가 나옵니다.
이 값은 세션 전체의 `cacheRead` 합계를 전체 prompt 토큰 합계로 나눈 것입니다.

이 누적값은 footer 값보다 낮게 나옵니다.
이유는 두 가지 miss가 섞이기 때문입니다.
miss는 캐시에서 읽지 못한 경우를 말합니다.

- 첫 호출: 아직 캐시가 없으니 완전히 miss입니다.
- 압축 직후 호출: 활성 문맥이 통째로 바뀌어 miss가 납니다.

::: warn 주의
두 수치는 분모가 다르게 구성됩니다.
그래서 둘을 서로 비교해 정책의 효과를 판단할 수 없습니다.
특정 시점에 캐시가 무너진 것은 footer 값에 드러납니다.
세션 전체의 과금 구조는 누적값에 드러납니다.
:::

세션 정보 화면은 따로 cache waste도 계산합니다.
직전 요청에 있었지만 캐시에서 읽지 못한 토큰을 모아 센 값입니다.

## 몇 번 만에 100% 가까이 가는 이유

비율이 빨리 오르는 비밀은 분모 구성에 있습니다.
프롬프트 하나는 이렇게 이루어집니다.

- system prompt (모델에게 주는 기본 지시문)
- tool 정의 (쓸 수 있는 도구의 설명서)
- 대화 이력
- 새로 붙은 메시지

코딩 에이전트에서는 system prompt와 tool 스키마가 수만 토큰에 이릅니다.
게다가 이 부분은 매번 똑같은 고정 구간입니다.
매 호출에 새로 붙는 것은 많지 않습니다.
사용자 메시지 수백 토큰이나 도구 결과 수천 토큰 정도입니다.

핵심은 이것입니다.
직전 호출의 프롬프트 전체가 다음 호출의 앞부분이 됩니다.
그러니 분자(재사용분)가 직전 분모와 거의 같아집니다.

::: analogy 비유 - 길어지는 기차
기차에 매번 칸이 하나씩 붙는다고 생각해 보십시오.
앞에 이미 있던 칸은 모두 재사용됩니다.
새로 만드는 것은 맨 끝 한 칸뿐입니다.
기차가 길어질수록 새 칸의 비중은 점점 작아집니다.
:::

### 4번의 호출로 계산해 보기

아래 표는 원문이 산식을 설명하려고 든 예시입니다.

| 호출 | 새로 추가된 내용 | cacheRead | cacheWrite | 표시 비율 |
|---|---|---|---|---|
| 1 | system + tools 30,000 · 사용자 메시지 500 | 0 | 30,500 | 0% |
| 2 | 도구 결과 3,000 | 30,500 | 3,000 | 91.0% |
| 3 | 다음 사용자 메시지 500 | 33,500 | 500 | 98.5% |
| 4 | 도구 결과 600 | 34,000 | 600 | 98.3% |

::: warn 주의
표의 토큰 수는 산식을 설명하려는 가정값입니다.
실제로 잰 값이 아닙니다.
각 호출에서 `input`은 0으로 두었습니다.
:::

한 줄씩 따라가 보겠습니다.

1. 첫 호출에는 캐시가 없습니다. 30,500토큰을 모두 써 넣기만 하니 0%입니다.
2. 두 번째 호출은 직전 30,500토큰을 그대로 읽습니다. 새 도구 결과 3,000만 씁니다. 30,500 / 33,500이라 91.0%입니다.
3. 세 번째는 33,500을 읽고 500만 씁니다. 98.5%가 됩니다.
4. 네 번째는 34,000을 읽고 600을 씁니다. 98.3%입니다.

네 번째가 세 번째보다 조금 낮은 것은 새 꼬리(600)가 조금 더 컸기 때문입니다.
그래도 분모가 커질수록 새 꼬리의 비중은 줄어 99%에 가까워집니다.

::: note 핵심
이 수렴은 컨텍스트 축소 정책의 성과가 아닙니다.
앞부분을 재사용하는 prefix cache의 산술적 성질입니다.
:::

## Anthropic 경로: 체크포인트를 어디에 찍는가

Anthropic Messages API는 표시가 붙은 지점까지만 캐시합니다.
그 표시가 `cache_control`입니다.
이 표시를 체크포인트라고 부르겠습니다.
"여기까지 앞부분을 저장해 둬"라는 책갈피라고 생각하면 됩니다.

이 하네스의 `anthropic-messages.ts`는 요청 하나에 최대 세 종류의 체크포인트를 둡니다.
여기에 두 가지 보조 처리가 더해집니다.

| 위치 | 하는 일 |
|---|---|
| system prompt | system 블록에 `cache_control: {type: "ephemeral"}`를 붙입니다. OAuth 토큰 경로에서는 Claude Code 식별 문장을 첫 블록에 두고, 그 뒤에 실제 system prompt를 둡니다. |
| tools | tool 정의의 마지막 항목에 표시합니다. `supportsCacheControlOnTools`가 참인 모델에만 해당합니다. Fireworks 경유 모델은 기본으로 빠집니다. |
| 마지막 user 메시지 | 변환된 메시지 배열의 마지막 user 또는 tool-result 메시지의 마지막 블록에 표시합니다. |
| tool loop 보존 | 마지막 메시지가 tool-result이고 그 앞이 tool-use인 연속 구간이면, 직전 user 체크포인트도 함께 남깁니다. |
| effort 마커 | `supportsMidConvoEffort` 모델은 이력 뒤에 effort 수준 마커가 붙습니다. 이 마커가 체크포인트를 밀어내지 않도록 진짜 마지막 user 메시지를 다시 찾아 표시합니다. |

### 마지막 user 표시가 왜 중요한가

이번 요청 끝에 찍은 표시는 다음 요청에서 힘을 씁니다.
다음 요청에서는 대화 이력 전체가 캐시 앞부분이 되기 때문입니다.
앞의 기차 비유에서 "지금까지 칸 전부 저장"이라고 적는 것과 같습니다.

### tool loop 보존은 왜 필요한가

도구를 연달아 쓰면 도구 결과가 계속 뒤에 붙습니다.
이때 앞선 캐시 경계가 사라지면 손해입니다.
그래서 직전 user 체크포인트도 함께 붙잡아 둡니다.

### 캐시는 얼마나 오래 남는가

보존 기간은 `cacheRetention` 설정으로 정합니다.
보존 기간을 TTL이라고 합니다. 저장된 캐시가 살아 있는 시간입니다.

- short: 기본값입니다. Anthropic 문서상 5분 TTL입니다.
- long: `PI_CACHE_RETENTION=long` 환경 변수나 모델 설정으로 켭니다. 1시간 TTL을 요청합니다.
- none: 체크포인트를 아예 붙이지 않습니다.

::: warn 주의
long을 켜도 언제나 1시간이 되는 것은 아닙니다.
요청 대상이 `api.anthropic.com`이고, 모델이 `supportsLongCacheRetention`일 때만 1시간 TTL을 요청합니다.
:::

응답의 `cache_creation_input_tokens`는 `cacheWrite`로 기록합니다.
1시간 캐시 쓰기는 `cacheWrite1h`로 따로 기록합니다.

## 다른 provider는 어떻게 하는가

체크포인트 방식은 Anthropic 계열만의 것입니다.
다른 provider는 두 가지 중 하나를 씁니다.

- 세션 식별자를 보내 캐시가 같은 곳으로 가도록 고정합니다.
- 서버가 알아서 적용한 캐시의 사용량만 읽습니다.

하네스는 provider마다 다른 필드 이름을 공통 `cacheRead`, `cacheWrite`로 맞춥니다.
그래서 footer 산식은 같아 보여도, 그 값 뒤의 실제 캐시 동작은 provider마다 다릅니다.

| 경로 | 요청에 넣는 것 | 사용량 해석 | 유의점 |
|---|---|---|---|
| Anthropic Messages | system·tools·마지막 user 블록의 `cache_control` | `cache_read_input_tokens`, `cache_creation_input_tokens` | TTL 5분 또는 1시간. 체크포인트 위치가 곧 캐시 경계입니다. |
| OpenAI Completions / Responses / Codex | `prompt_cache_key`에 세션 ID를 64자로 잘라 전달. long이면 `prompt_cache_retention: 24h` | `prompt_tokens_details.cached_tokens`. DeepSeek의 `prompt_cache_hit_tokens`, Kimi의 최상위 `cached_tokens`도 같은 필드로 정규화 | 쓰기 토큰이 보고되지 않는 경우가 많아 `cacheWrite`가 0으로 남습니다. 키는 라우팅 힌트일 뿐, 캐시 경계를 정하지 않습니다. |
| Google Generative AI / Vertex | 없음. 서버의 암묵적 캐시에 의존 | `cachedContentTokenCount`를 `cacheRead`로, 나머지를 `input`으로 계산 | TTL을 알 수 없어 TTL 기반 대기 예산이 적용되지 않습니다. |
| Bedrock Converse | system과 메시지에 `cachePoint`. 모델이 지원하면 1시간 TTL | Anthropic과 같은 읽기·쓰기 구분 | `supportsPromptCaching` 판정을 통과한 모델에만 해당합니다. |
| Mistral Conversations | `promptCacheKey`에 세션 ID | `cached_tokens` 계열 필드를 정규화 | 명시적 affinity가 있으면 키를 넣지 않습니다. |

::: warn 주의
OpenAI 계열에서 `cacheWrite`가 0이라고 해서 캐시 쓰기가 없었다는 뜻은 아닙니다.
보고되지 않아 0으로 남는 경우가 많다는 뜻입니다.
또 이 표는 요청 조립 코드에서 확인한 기본 동작입니다.
게이트웨이나 호환 provider는 compat 설정으로 항목을 끄고 켤 수 있습니다.
같은 API 형식이라도 모델 설정에 따라 실제 동작이 달라집니다.
:::

## 캐시를 지키는 하네스 장치

체크포인트가 캐시를 만든다면, 아래 장치들은 그 캐시가 낭비되지 않게 합니다.
시간과 요청 모양을 관리하는 방식입니다.
앞 장의 축소 정책 중 히스테리시스와 결정적 변환도 같은 목적을 가집니다.

### 270초: TTL을 넘기지 않는 도구 대기

`promptCache.cacheAwareTimeouts`는 기본으로 켜져 있습니다.
전경 도구가 응답을 기다리는 시간을 제한합니다.
한도는 모델의 캐시 TTL에서 30초를 뺀 값입니다.
5분 TTL이면 270초입니다.

한도에 닿은 bash 명령은 죽이지 않습니다.
대신 백그라운드 세션으로 넘깁니다.
그래야 다음 모델 호출이 캐시가 만료되기 전에 나갈 수 있습니다.
TTL을 모르는 모델에는 이 예산이 적용되지 않습니다.

::: analogy 비유 - 주차 시간
무료 주차가 5분이라면, 4분 30초쯤 차를 빼야 요금이 안 붙습니다.
일이 덜 끝났다면 일을 버리지 않고 다른 곳에 맡겨 둡니다.
:::

### keepalive: 쉬는 동안 캐시 갱신 (기본 꺼짐)

`cache-keepalive` 확장은 세션이 쉬고 있을 때 동작합니다.
TTL이 끝나기 전에 warm ping이라는 작은 요청을 보내 캐시를 살려 둡니다.

- 기본은 꺼져 있습니다.
- 켜더라도 세션당 3회, 0.05달러 상한을 지킵니다.
- ping 간격은 TTL에서 30초를 뺀 안전 대기 시간에 다시 60초 여유를 둔 값입니다.
- 직접 Anthropic 연결에서만 동작합니다.
- 대기 메시지가 있거나 에이전트가 바쁘면 멈춥니다.

::: note 핵심
이 확장을 켜지 않았다면, 100%에 가까운 표시는 이 확장과 관련이 없습니다.
:::

### 캐시 친화적 요약: 요약 요청도 앞부분 재사용

이것은 실험 기능입니다.
켜져 있으면 요약 생성 요청이 대화를 텍스트로 바꿔 보내지 않습니다.
대신 지금 provider에 보내던 내용과 정확히 같은 앞부분을 그대로 보냅니다.

조건이 있습니다.
요약할 구간이 현재 요청의 앞부분과 `isDeepStrictEqual`로 완전히 일치해야 합니다.
일치하면 요약 요청에도 캐시 단가가 붙을 여지가 생깁니다.
일치하지 않으면 원래의 직렬화 방식으로 돌아갑니다.

## 캐시가 깨지는 지점과 감지

`cache-stats.ts`는 assistant 메시지마다 직전 요청과 비교해 miss를 계산합니다.

```text
missedTokens = min(prevPromptTokens, promptTokens) − cacheRead
counted if missedTokens > 1024
```

풀어 쓰면 이렇습니다.
직전 프롬프트 토큰과 현재 프롬프트 토큰 중 작은 값을 고릅니다.
거기서 캐시에서 읽은 양을 뺍니다.
남은 값이 "읽을 수 있었는데 못 읽은 양"입니다.
이 값이 1024토큰을 넘으면 miss로 셉니다.

이때 두 가지를 함께 적어 둡니다.

- 직전 요청 뒤 지난 시간
- 모델이 바뀌었는지

지난 시간이 5분을 넘으면 TTL 만료를 원인 후보로 표시합니다.
캐시 활동을 한 번도 보고하지 않은 provider에서는 miss를 세지 않습니다.

### 앞부분이 바뀌는 원인들

구현에서 확인되는 원인은 다음과 같습니다.

- **압축 적용**: 활성 문맥이 통째로 바뀝니다. 그 직후 호출은 새 내용으로 보고 miss 집계에서 뺍니다.
- **모델 전환**: 프롬프트 전체를 다시 과금하므로 miss로 셉니다.
- **축소 단계가 바뀌는 세 순간**: 50% gate를 처음 넘는 순간, clearable 도구 결과의 최근 6개 창이 밀리는 순간, emergency latch가 켜지는 순간입니다. 이때 앞부분의 중간이 바뀝니다.
- **날짜 변경**: system prompt에는 `Current date`가 들어 있습니다. 날짜가 바뀐 뒤 프롬프트를 다시 만들면 system 블록 캐시도 새로 쓰입니다.

## 인과를 거꾸로 읽지 마십시오

여기가 이 장에서 가장 중요한 단서입니다.

높은 적중률을 만드는 것은 두 가지입니다.
체크포인트 배치, 그리고 큰 고정 앞부분입니다.
컨텍스트 정책은 그 앞부분을 쓸데없이 바꾸지 않도록 설계되어 있을 뿐입니다.

그러니 "정책 덕분에 적중률이 높다"고 말하면 인과가 뒤바뀝니다.
정책은 캐시를 만들지 않습니다.
캐시를 덜 깨뜨리도록 비켜 서 있는 쪽입니다.

::: note 핵심
정책의 효과를 보고 싶다면 세션 평균을 보면 안 됩니다.
압축 직후, 그리고 축소 단계가 바뀐 직후 호출의 footer 값과 cache waste를 봐야 합니다.
:::

## 한 줄 정리

footer의 `CH`는 가장 최근 호출 하나의 `cacheRead / (input + cacheRead + cacheWrite)`이고, `/session`의 누적값은 첫 호출과 압축 직후 miss가 섞여 더 낮습니다.
적중률이 금방 90%대로 오르는 것은 큰 고정 앞부분을 재사용하는 산술적 성질 때문입니다.
하네스는 체크포인트 배치, 270초 도구 대기, 선택적 keepalive, miss 감지로 캐시를 지킵니다.
높은 적중률은 정책이 만든 것이 아니며, 정책은 그 앞부분을 깨지 않도록 돕는 역할입니다.
