# 02 · 왜 컨텍스트 관리가 필요한가 — 창은 한계이고, 모델은 매번 처음부터 다시 읽는다

> **한 줄 요약:** 모델은 지난 대화를 기억하지 못해 하네스가 호출마다 대화 전체를 다시 보내므로, 대화가 길어질수록 보내는 토큰이 늘고 결국 컨텍스트 창이라는 벽에 부딪힙니다.

## 이 장에서 배우는 것

- 하네스가 왜 호출마다 대화 전체를 다시 보내는지
- 요청 하나가 왜 모델 호출 여러 번이 되는지
- 긴 대화가 토큰 면에서 점점 무거워지는 이유와 창이라는 벽
- 이 자료가 세울 두 층의 답(규칙 먼저, 요약은 그다음)

## 왜 이 이야기부터 하는가

컨텍스트 관리는 결국 "무엇을 줄이려는가"의 문제입니다.
줄이려는 대상을 모르면 뒤의 규칙들이 왜 있는지 알 수 없습니다.
이 자료가 줄이려는 것은 하나입니다.
모델에 보내는 토큰입니다.

## 모델은 매번 처음부터 다시 읽는다

먼저 알아 둘 사실이 있습니다.
모델은 지난 대화를 스스로 기억하지 않습니다.
호출이 끝나면 모델 쪽에는 아무것도 남지 않습니다.
그래서 하네스가 호출할 때마다 지금까지의 대화를 다시 보냅니다.

이렇게 모델에 실제로 보내는 입력 묶음을 **프롬프트**라고 합니다.
프롬프트에는 보통 이런 것들이 들어갑니다.

- system prompt: 모델에게 주는 기본 지침
- tool 정의: 모델이 쓸 수 있는 도구 목록과 사용법
- 대화 이력: 지금까지 오간 메시지와 도구 결과
- 새로 추가된 메시지

앞의 두 가지는 대화가 길어져도 거의 그대로입니다.
늘어나는 것은 대화 이력입니다.
새 메시지가 붙을 때마다 이력은 길어집니다.
따라서 프롬프트도 호출마다 조금씩 커집니다.

## 요청 하나는 호출 하나가 아니다

사용자의 요청 하나가 모델 호출 한 번은 아닙니다.
모델이 도구를 쓰면, 하네스는 도구를 실행합니다.
그리고 그 결과를 붙여 모델을 다시 부릅니다.
도구를 다섯 번 쓰면 호출도 다섯 번 생깁니다.

원문은 사용자 요청 세 번이 호출 열 번 이상일 수 있다고 설명합니다.
그런데 호출마다 대화 전체가 다시 실립니다.
도구 결과도 이력에 쌓이므로, 다음 호출은 더 무거워집니다.
긴 파일을 한 번 읽으면 그 내용이 이후 호출마다 따라다닙니다.

## 긴 대화는 왜 점점 무거워지는가

대화가 길어지면 다음 일이 차례로 일어납니다.

1. 메시지와 도구 결과가 쌓여 대화 이력이 길어집니다.
2. 모델은 기억이 없으니 그 이력을 호출마다 다시 받습니다.
3. 그래서 호출 한 번에 보내는 토큰이 계속 늘어납니다.
4. 호출 수도 요청보다 많으니, 늘어난 양이 여러 번 반복됩니다.

::: analogy 비유 — 점점 두꺼워지는 회의 자료
회의 때마다 지난 회의록 전체를 다시 인쇄해 나눠 준다고 해 봅시다.
참석자는 지난 회의를 기억하지 못해서 매번 처음부터 읽어야 합니다.
회의가 거듭될수록 나눠 주는 자료는 두꺼워집니다.
안건 하나를 처리하는 데 회의를 여러 번 열면, 두꺼운 자료가 그만큼 여러 번 인쇄됩니다.
어느 순간 자료가 책상에 다 올라가지 않습니다.
:::

## 창이라는 벽

양이 늘어나는 것에는 끝이 있습니다.
바로 **컨텍스트 창**입니다.
모델이 한 번에 볼 수 있는 토큰의 최대 개수입니다.
원문은 200k(20만 토큰) 창을 자주 예로 듭니다.

창은 넘을 수 없는 벽입니다.
프롬프트가 창보다 크면 그 호출은 보낼 수 없습니다.
그래서 벽에 닿기 전에 무언가를 줄여야 합니다.
아무것도 하지 않으면 긴 대화는 언젠가 멈춥니다.

::: note 핵심
토큰을 줄이는 이유는 두 가지입니다.
보내는 양이 곧 처리할 양이라서, 그리고 창을 넘으면 아예 보낼 수 없어서입니다.
:::

## 실제 세션 기록으로 보기

원문은 이 모습을 실제 기록으로 보여 줍니다.
보고서를 만든 컴퓨터에서 메시지가 가장 많았던 세션입니다.
여기 나오는 숫자는 세션 로그에서 가져온 **실측값**입니다.

| 항목 | 값 |
|---|---|
| 기간 | 2026-09-27 ~ 09-30, 약 50시간 |
| 메시지 | 4,883개 |
| 모델 호출 | 2,387번 |
| 컴팩션 | 11회 |
| 세션 시작 프롬프트 | 33,845토큰 |
| 첫 컴팩션 직전 | 238,875토큰 |
| 세션 최대 프롬프트 | 307,310토큰 |
| 마지막 호출 | 63,379토큰 |

메시지 4,883개를 처리하는 데 모델 호출이 2,387번 있었습니다.
시작할 때 프롬프트는 33,845토큰이었습니다.
대화가 쌓이면서 첫 컴팩션 직전에는 238,875토큰까지 커졌습니다.
가장 클 때는 307,310토큰이었습니다.
그 사이 컴팩션이 11번 일어나 프롬프트를 크게 접었습니다.
마지막 호출은 63,379토큰이었습니다.

원문의 재생 그래프에서 막대가 차오르는 것은 새 메시지가 쌓이는 순간입니다.
잠깐 내려가는 것은 규칙에 따른 축소입니다.
크게 접히는 것은 컴팩션입니다.

::: warn 주의
이 값은 제공자가 보고한 사용량 필드를 그대로 쓴 것입니다.
모델별 창 크기는 로그에 남지 않았습니다.
그래서 그래프 축은 관측 최대값보다 조금 큰 320,000토큰으로 고정했습니다.
프롬프트 값이 빈 호출 78개는 건너뛰었습니다.
가로축은 10분 넘게 메시지가 없던 25곳(합계 36.4시간, 최장 17.4시간)을 잘라 낸 활동 시간, 약 13.8시간 기준입니다.
이 기록은 장치가 움직인 모습을 보여 줄 뿐, 절감 효과를 계산한 것은 아닙니다.
:::

## 이 자료가 세울 두 층의 답

그렇다면 하네스는 어떻게 줄일까요?
이 자료는 답을 두 층으로 나눠 설명합니다.

| 층 | 하는 일 | LLM 호출 |
|---|---|---|
| 1층, 규칙 | 메시지의 종류, 위치, 크기만 보고 보낼 내용을 자릅니다 | 필요 없음 |
| 2층, 요약 | 그래도 부족하면 오래된 대화를 요약으로 바꿉니다 | 대개 필요함 |

1층은 요청 투영 단계에서 돕니다.
도구 출력 입장 제한, 50% 축소 관문, 95/85 긴급 축소가 여기에 속합니다.
2층은 컴팩션입니다.
언제 2층으로 넘어갈지는 임계값이 정합니다.
각 장치는 뒤의 장에서 하나씩 풀어 설명합니다.

::: analogy 비유 — 자료를 줄이는 두 방법
먼저 회의 자료에서 지난번 긴 첨부물을 "첨부 생략"으로 바꿔 인쇄합니다. 이것이 1층입니다.
그래도 두꺼우면 지난 회의들을 한 장짜리 요약으로 정리해 그것만 나눠 줍니다. 이것이 2층입니다.
:::

## 원문은 무엇을 재고, 무엇을 재지 않았나

위 세션 기록을 빼면 원문은 아무것도 측정하지 않았습니다.
원문은 코드를 읽고 조건을 밝혔습니다.
"이 조건이 되면 이 장치가 움직인다"까지가 원문의 범위입니다.
각 층이 실제로 토큰을 얼마나 줄이는지는 같은 작업 조건에서 따로 재야 합니다.

## 한 줄 정리

모델은 기억이 없어서 하네스가 호출마다 대화 전체를 다시 보냅니다.
요청 하나가 호출 여러 번이 되고 이력은 계속 쌓이므로, 긴 대화일수록 보내는 토큰이 늘다가 컨텍스트 창이라는 벽에 닿습니다.
하네스는 먼저 규칙으로 자르고, 그래도 부족하면 요약으로 바꾸는 두 층으로 이 문제에 답합니다.
