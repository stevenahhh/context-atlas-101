# 12 · 흔한 오해 바로잡기 — 다 읽은 사람이 자주 틀리는 다섯 가지

> **한 줄 요약:** 이 하네스의 축소 장치들은 대부분 "조건이 붙은 동작"이므로, 숫자 하나나 이름 하나만 기억하면 실제와 다르게 설명하게 됩니다.

## 이 장에서 배우는 것

- 보내는 토큰을 줄이는 로직을 설명할 때 자주 틀리는 다섯 가지 문장
- 각 문장이 실제 구현과 어떻게 다른지
- 왜 그런 착각이 생기기 쉬운지, 다음에 같은 실수를 피하는 방법

## 왜 이 장이 필요한가

앞 장들을 다 읽고 나면 큰 그림은 잡힙니다. 먼저 규칙으로 보낼 내용을 자르고, 그래도 부족하면 오래된 대화를 요약으로 바꾸는 구조입니다. 이 큰 그림 자체는 대체로 맞습니다.

문제는 세부입니다. 원문 보고서는 기존 설명을 코드와 하나씩 대조했습니다. 그랬더니 숫자의 기준을 바꿔 읽은 경우가 있었습니다. 어느 한 경로에서만 맞는 조건을 정책 전체의 약속처럼 말한 경우도 있었습니다.

원문은 이런 차이를 두 종류로 나눕니다.

- **정정:** 구현과 다른 내용입니다. 그대로 말하면 틀립니다.
- **조건부:** 적용 범위나 추가 조건을 밝혀야만 맞는 설명입니다. 조건을 빼면 틀린 말이 됩니다.

아래 다섯 항목은 이 순서를 따릅니다. 1~3번은 정정, 4~5번은 조건부입니다. 각 항목은 "오해 → 실제 → 왜 헷갈리는가" 순서로 읽으면 됩니다.

## 오해 1. 복원 장치가 파일과 스킬 본문을 되살려 준다

::: warn 오해
요약 뒤에 restoration tracker가 파일·스킬 본문을 복원해 줍니다. 그래서 같은 파일을 다시 읽는 일이 줄어듭니다.
:::

::: note 실제 (정정)
restoration tracker가 다시 넣어 주는 것은 세 가지뿐입니다. **파일 경로, 작업 종류(operation), 스킬 이름**입니다. 본문을 다시 읽어 오지 않습니다. 스킬 지침을 다시 불러오지도 않습니다.
:::

비유하면 이렇습니다. 책상을 치운 뒤 "아까 이 책 몇 쪽을 봤다"는 쪽지만 남기는 것입니다. 책 내용을 다시 펼쳐 두는 것은 아닙니다.

남길 항목을 고르는 순서도 흔히 오해합니다. 최근에 쓴 것부터 고르지 않습니다. 실제 순서는 다음과 같습니다.

1. 우선순위가 높은 것
2. 짧은 항목
3. 이름순

그렇다면 효과가 전혀 없을까요? 그렇지는 않습니다. 관련 대상을 모델에게 상기시키는 효과는 기대할 수 있습니다. 하지만 이름만 남았다고 해서 다음 작업에 필요한 본문을 확보한 것은 아닙니다. "파일 재독 횟수나 비용이 줄었다"는 결론은 실제 실행을 관찰해야만 내릴 수 있습니다.

**왜 헷갈리는가:** "복원(restoration)"이라는 이름 때문입니다. 이름만 보면 원래 내용을 되돌려 놓는 기능처럼 들립니다. 실제로는 목록을 다시 적어 주는 쪽에 가깝습니다. 근거 [08]

## 오해 2. 800토큰 넘는 옛 답변을 원래 길이의 30%로 줄인다

::: warn 오해
800토큰이 넘는 오래된 답변은 원래 길이의 30%로 잘립니다. 2000토큰짜리 답변이면 600토큰이 남습니다.
:::

::: note 실제 (정정)
30%의 기준은 원래 답변 길이가 아닙니다. **설정값 800토큰의 30%, 약 240토큰**이 남길 본문의 목표입니다. 원문이 2000토큰이어도 600토큰을 남기지 않습니다. 그리고 최종 결과에는 줄였다는 표시(축소 마커)가 덧붙습니다.
:::

적용 대상도 좁습니다. 두 조건을 모두 만족해야 합니다.

- 최근 보호 구간 **밖**에 있는 메시지
- 도구 호출 없이 글만 있는 **텍스트 전용 assistant 메시지**

이 조건을 빼고 "30%로 줄인다"만 전하면 어떻게 될까요? 듣는 사람은 최근 답변이나 도구 호출이 섞인 메시지도 똑같이 줄어든다고 생각하게 됩니다. 그것은 사실이 아닙니다.

**왜 헷갈리는가:** "800토큰"과 "30%"가 한 문장에 함께 나오기 때문입니다. 자연스럽게 "그 메시지의 30%"로 읽게 됩니다. 실제로는 "800의 30%"입니다. 기준이 메시지가 아니라 설정값입니다. 근거 [04]

## 오해 3. 효과 없는 요약은 circuit breaker가 걸러 낸다

::: term 용어 — circuit breaker
여러 번 실패한 작업을 잠시 멈추게 하는 차단 장치입니다. 전기 차단기처럼, 문제가 반복되면 한동안 시도를 막습니다.
:::

::: warn 오해
요약을 했는데 별로 줄지 않으면(비효율 요약), circuit breaker가 이를 감지하고 막아 줍니다.
:::

::: note 실제 (정정)
비효율(ineffective) 카운터와 실패 breaker는 현재 **직접 연결되어 있지 않습니다.** 그리고 상한(cap)을 판정하는 `shouldRejectByCap()`은 **항상 허용**하는 값을 돌려줍니다.
:::

실제 흐름을 순서대로 보면 이렇습니다.

1. 요약이 받아들여지면 먼저 **성공**으로 기록됩니다.
2. 성공 기록은 실패 횟수를 0으로 되돌립니다.
3. "절약량이 작았다"는 사실은 별도 카운트와 로그로만 남습니다.

즉 두 장치는 따로 놉니다. 하나는 실패를 반복한 작업에 cooldown(쉬는 시간)을 거는 장치입니다. 다른 하나는 성공했지만 절약량이 작은 요약을 세어 두는 장치입니다. 앞의 것이 뒤의 것을 막지 않습니다.

코드 주석에는 차단하려는 의도가 보입니다. 하지만 의도는 보장이 아닙니다. 지금 실행되는 코드가 그렇게 동작한다고 인용할 수는 없습니다.

**왜 헷갈리는가:** 이름과 주석이 그럴듯하기 때문입니다. "ineffective"와 "breaker"가 같은 곳에 있으면 둘이 이어져 있다고 짐작하기 쉽습니다. 근거 [09]

## 오해 4. 기록 손실이 없고, 항상 더 싸고 빠르다

::: warn 오해
원본 기록이 남아 있으니 잃는 정보가 없습니다. 그러니 항상 더 싸고 더 빠릅니다.
:::

::: note 실제 (조건부)
**저장된 원본을 보존하는 것**과 **요청에 정보를 담는 것**은 다릅니다. 이번 모델 요청에서 뺀 본문은 모델 입력에 들어가지 않습니다.
:::

창고에 서류가 남아 있어도, 회의 책상 위에 없으면 회의에서는 볼 수 없습니다. 발췌와 마커가 필요한 정보를 충분히 남겼는지는 작업마다 다를 수 있습니다.

"더 싸고 빠르다"도 그냥 말할 수 없습니다. 실제 비용을 평가하려면 다음을 함께 봐야 합니다.

- 요청량이 얼마나 줄었는지
- 요약을 만들고 버린 횟수
- 뺀 정보를 다시 찾느라 든 노력(재탐색)

원문 보고서는 실행 조건을 분석한 자료입니다. 비용이나 지연을 실제로 잰 결과는 들어 있지 않습니다.

**왜 헷갈리는가:** "원본 보존"이라는 말이 안심을 줍니다. 그래서 모델도 모든 것을 보고 있다고 착각하게 됩니다.

## 오해 5. 이 하네스는 pi보다 컴팩션을 더 늦게 한다

::: warn 오해
이 하네스는 upstream pi보다 요약을 더 늦게 합니다.
:::

::: note 실제 (조건부)
직전 yield 조정이 없는 기본 200k 창을 기준으로 보겠습니다. 이 하네스의 요약 admission(요약을 받아들일지 판단하는 단계) 임계값은 **140,000토큰**입니다. 비교한 upstream pi의 기본 조건은 **183,616토큰 초과**입니다. 그러니 이 기준에서는 이 하네스가 요약을 **더 일찍** 고려합니다.
:::

숫자로 보면 차이가 분명합니다.

| 비교 대상 | 요약을 고려하는 기준 (기본 200k 창) |
|---|---|
| 이 하네스 | 140,000토큰 |
| upstream pi | 183,616토큰 초과 |

다만 이것은 **admission 기준끼리의 비교**입니다. 요약이 실제로 언제 일어나는지까지 한 번에 비교한 것은 아닙니다. 원문은 요약에 관련된 시점을 여러 개로 나눠 봐야 두 시스템을 같은 기준으로 비교할 수 있다고 말합니다. 그래서 "더 일찍 고려한다"까지만 말하는 것이 정확합니다.

**왜 헷갈리는가:** 이 하네스는 1층의 규칙 축소를 먼저 거칩니다. 그래서 요약이 뒤로 밀린다고 짐작하기 쉽습니다. 하지만 요약을 고려하는 문턱 자체는 더 낮습니다. 근거 [12]

## 다섯 가지를 관통하는 공통점

다섯 오해에는 비슷한 패턴이 있습니다.

- **이름이나 주석을 믿었습니다.** (오해 1, 3)
- **숫자의 기준을 바꿔 읽었습니다.** (오해 2, 5)
- **층위가 다른 것을 하나로 묶었습니다.** (오해 4)

설명할 때 스스로 물어보면 좋습니다. "이 숫자의 기준은 무엇인가?", "이 조건은 어느 메시지에만 해당하는가?", "저장된 원본과 이번 요청에 보낸 내용이 같은가?"

## 한 줄 정리

이 하네스의 축소 구조는 대체로 알려진 대로이지만, 세부 동작에는 조건이 붙어 있습니다. 복원은 이름만 남기고, 30%는 800토큰의 30%이며, breaker는 비효율 요약을 막지 않습니다. 원본 보존은 요청에 정보가 담긴다는 뜻이 아니고, 요약 admission 문턱은 pi보다 낮습니다. 숫자를 인용할 때는 그 기준과 적용 범위를 함께 말해야 맞는 설명이 됩니다.
