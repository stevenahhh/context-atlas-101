04 INTERACTIVE POLICY GEOMETRY
적응 임계값과 토큰 예산의 계산
요청 축소와 별도로, 이 하네스는 창 크기와 직전 요약의 절약률을 이용해 요약을 시작할 시점을 정하는 admission 임계값을 계산한다. 아래 실험은 기본 정책의 수식을 재현하며 실제 세션이나 모델을 호출하지 않는다. 입력 사용량에는 pending prompt의 추정량이 이미 포함되었다고 가정한다. 이 값과 도구 출력을 축소한 뒤 provider에 전달하는 요청량은 서로 다를 수 있다. [06]
차트는 여러 경계를 같은 전체 창 C 위에 배치한다. 기본 200k 예시에서는 100,000토큰부터 일반 reduction과 유휴 warm 생성의 조건이 성립하고 122,500토큰에서 pre-turn speculative 시작점에 도달한다. 요약 임계값은 140,000토큰이지만 미완성 job이 있으면 157,500토큰 미만에서 blocking을 유예할 수 있다. 따라서 생성 시작점, 적용 판단, blocking 실행의 경계를 하나의 ‘압축 시점’으로 묶으면 실제 동작을 놓치게 된다.

요청 축소 선행 준비 요약·한계 입력 사용량
차트의 세로 표시는 입력 사용량과 각 경계의 상대적 위치를 나타낸다. 어떤 경계에 도달했다는 사실이 해당 작업의 즉시 실행을 보장하지는 않는다. 출력 한도를 반영한 긴급 축소 경계는 별도 수치로 제시하며 이 입력 사용량만으로 emergency-prune의 발동 여부를 판정하지 않는다. 창 밖에 놓이는 경계도 숫자는 그대로 표시하고 막대의 시각적 범위만 0~100%로 제한한다.
창 크기와 직전 절약률의 반영
기본 임계 비율은 창 크기에 따라 단계적으로 달라진다. 직전 요약이 압축 전 토큰의 50%를 넘게 절약했다면 기본값에서 5%p 낮춘다. 절약률이 그 이하이면 기본 비율을 사용한다. 매 판단은 기본 비율에서 다시 계산한다.

Compaction reserve와 출력 reserve
Compaction reserve 는 하드 리밋과 grace 등의 계산에 쓰인다. 기본 설정은 16,384토큰이다. Scaling이 활성화되면 창의 4%를 계산해 설정값과 비교하되, 창 크기로 계산하는 항은 최대 49,152토큰으로 제한한다. 설정값 자체가 그보다 크면 더 큰 설정값을 유지하므로 49,152를 모든 reserve의 절대 상한으로 읽어서는 안 된다.
R = max(configured,
min(floor(C × 0.04), 49,152))
출력 reserve 는 emergency-prune에서 사용할 프롬프트 공간을 정한다. 이 계산에서는 모델의 maxTokens 와 창의 절반 중 작은 값을 제외한다. 두 reserve는 목적과 입력값이 다르므로, 한쪽을 변경했을 때 다른 쪽 경계도 같은 양만큼 이동한다고 가정할 수 없다.
토큰 예산 리마인더는 모델의 행동을 조정하려는 별도 장치이다. 임계값까지 남은 양이 양수이고 lead의 두 배 이내이면, 같은 generation에서 한 번 남은 예산을 안내한다. 기본 200k 예시의 구간 시작점은 105,000토큰이다. 이 안내는 탐색과 답변을 간결하게 하도록 유도하지만 이후 모델이 소비할 토큰 수를 강제하는 제한이나 실제 절약량의 보장은 아니다.
수식과 실행 상태의 구분. 계산기는 경계의 위치와 명시한 job 조건에 따른 분기를 보여 준다. 실제 실행에는 요약 결과의 유효성, 세션의 유휴 여부, provider 소유권, 실패 상태가 추가로 관여한다. 이 실험의 분기 설명을 실시간 세션 관측 결과로 해석해서는 안 된다.
