09 IMPLEMENTATION COMPARISON
Codex와 Claude Code의 구현과 비교
컨텍스트 관리와 프롬프트 캐시는 이 하네스만의 문제가 아니다. 같은 과제를 풀고 있는 두 코딩 에이전트 구현체와 나란히 놓으면 어떤 선택이 공통 설계이고 어떤 것이 이 구현의 특징인지 드러난다. Codex는 오픈소스라 구현 자체를 대조할 수 있고(clone HEAD d4205609 ), Claude Code는 소스가 비공개라 공식 문서와 로컬 세션의 usage 필드 관측으로 한정한다. Claude Code의 행은 문서가 보장하는 범위의 서술이며 코드 수준의 단정이 아니다. [17] [18]
세 구현체 모두 공통의 토대 위에 있다. 요약에는 현재 대화의 모델을 그대로 쓴다. 요약 입력에는 공통 요약 지시를 마지막 사용자 메시지로 붙인다. 최근 대화 구간은 일부 보존한다. 캐시에는 세션 식별자나 prefix 일치가 관여한다. 차이는 토대 위의 분기에서 생긴다. Codex에는 세 경로가 있다. 원격 compaction을 지원하는 모델이면 서버에 CompactionTrigger 아이템을 보내 서버가 만든 Compaction 출력을 받는다. Feature::TokenBudget이면 요약 없이 새 컨텍스트 윈도우를 설치한다. 둘 다 아니면 로컬 요약을 수행한다. Claude Code는 로컬 요약 경로 하나에 서버 측 context editing이 병존한다. 이 하네스는 요약 이전에 결정적 축소 층을 둔다. [17] [18]

Codex 열은 클론 d4205609의 codex-rs 소스, Claude Code 열은 공식 문서와 usage 필드 관측에 근거한다. Codex는 원격 compaction 지원 모델에서 로컬 요약을 거치지 않고 Claude Code의 context editing은 서버가 처리하므로 클라이언트 측 변환 코드와 무관하다.
로컬 관측: usage 필드가 말해 주는 것
두 구현체의 세션 로그를 이 장비에서 읽었다. Claude Code 세션에서는 호출당 cache_read_input_tokens 가 최대 약 738,000까지 쌓이고 cache_creation_input_tokens 는 수천~만 토큰에 그쳐 한 세션 내에서는 거의 전량이 캐시 읽기로 처리됐다. usage에 ephemeral_1h · ephemeral_5m 필드가 구분돼 나타나 TTL 버킷이 실제로 다르게 기록됨을 보인다. Codex의 rollout 로그는 cached_input_tokens · cache_write_input_tokens 를 누적 기록한다.
관측의 해석에는 한계가 있다. 표본 세션에서는 두 구현체 모두 자동 요약 이벤트를 찾지 못했고 Claude Code의 관찰 대상 세션은 context_management: null 로 context editing이 비활성이었다. 이는 기능의 부재가 아니라 해당 세션이 기능 경계에 도달하지 않았거나 설정이 꺼져 있었음을 의미한다. 요약·편집의 실제 행동은 해당 세션이 임계값을 넘겼을 때만 드러나므로, 이 관측은 필드 구조와 캐시 사용 패턴의 확인에 한정한다. [19]
이 하네스의 차이는 어디에 있는가
대조한 두 구현체에서 이 하네스의 특징이 세 갈래로 드러난다. 첫째, 요약 이전의 결정적 축소 층 이다. Codex는 도구 출력을 기록 시점에 한 번 자른다. 지우는 일은 요약이 맡는다. Claude Code는 오래된 tool uses 치환을 서버에 맡긴다. 이 하네스는 provider 요청마다 규칙으로 도구 출력과 답변을 다시 줄인다. 그래서 같은 대화라도 요약 도달 시점이 늦어진다. 둘째, 요약 대기의 숨기기 다. Codex와 Claude Code의 자동 요약은 도달한 턴에 즉시 동기 실행되므로 그 호출이 늦어지는데, 이 하네스는 임계값 앞 lead와 유휴 시간에서 미리 생성해 둔다. 셋째, 실패 관리 다. 요약 실패의 circuit breaker와 무텍스트 응답 감시에 해당하는 장치는 두 구현체에서 확인되지 않았다.
반대 방향의 차이도 있다. Codex는 원격 compaction을 지원하는 모델에서 요약 자체를 서버에 위임하고 Feature::TokenBudget으로 요약 자체를 생략하는 분기가 있어 더 큰 구조적 선택지를 둔다. Claude Code는 요약 이후 CLAUDE.md·메모리·최근 수정 파일 5개·스킬 본문을 디스크에서 다시 읽어 붙이는 복원 단계가 문서에 명시되어 있고 서버 측 context editing은 클라이언트 구현 없이 같은 효과를 낸다. 이 하네스의 restoration tracker가 라벨만 재주입해 세부 본문 복원은 하지 않는 대조점이다.
비교의 비대칭. Codex는 소스 전체를 읽을 수 있으므로 각 셀이 코드 확인 값이고 Claude Code는 문서와 usage 관측이 근거다. "문서에 없음"은 "구현에 없음"이 아니며 Claude Code 행의 부재 표시는 모두 관측 범위 한정으로 읽어야 한다. [20]
